## 载体决策（第一步，不可跳过）

先回答"这块 UI 是什么东西"，再谈它长什么样。载体错了，后面每一步都会朝错的方向优化。

| 载体 | 定义 | 实现层 | 典型例子 |
| ---- | ---- | ------ | -------- |
| **A. 世界内装置（diegetic）** | 玩家角色在游戏世界里实际看到/操作的东西 | Phaser 层（Graphics / sprite / 世界坐标） | HUD 读数、地面标记、交互提示、边界表现 |
| **B. 世界内终端** | 世界里存在的一块屏幕/仪表，玩家借它操作 | DOM overlay，但视觉上必须是"那台设备的屏幕" | 净化点各管理面板 |
| **C. 元界面** | 承认自己在游戏之外的界面 | DOM | 主菜单、设置、语言切换 |

**本模块的载体**：[A / B / C]
**理由**：[一句话]

> **约束**：只有 C 允许有"软件界面感"。A 和 B 必须读起来像世界里的物件——它们的视觉合理性来自世界观（材质、磨损、供电状态、字体来自哪台机器），不来自"现代 UI 好看"。

## 游戏内 UI 验收清单（全项目权威清单）

QA 与人在验收任何触碰 UI 的 Slice 时逐条过。**任一条不通过即为偏差**，需在 QA 报告中记为 UI 偏差并指出所违反的条目号。

- [ ] **U1 载体正确**：世界内装置/终端没有被做成"游戏外的软件界面"；只有元界面允许软件感
- [ ] **U2 无后台管理气味**：无圆角卡片堆砌、无投影/发光、无渐变按钮、无通用图标字体、无 Material/Bootstrap 味配色。直角 + 1px 边框 + 锁定色板
- [ ] **U3 色彩合规**：只用 `palette.json` 锁定色与 `art-direction.md` 定义的语义色，未引入新色值
- [ ] **U4 排版合规**：字体族与字号层级在 `ui-art-overhaul.md` A2 范围内，未自造字号
- [ ] **U5 术语合规**：所有可见文本用 `world.md` 术语表用词；无"提交/确认/设置/物品栏/OK/保存成功"这类通用软件词
- [ ] **U6 不遮挡**：游戏进行中的 UI 不占据画面中心与玩家周围可视区；面板走屏幕边缘/侧栏
- [ ] **U7 输入一致**：提示的按键 = 实际绑定；键盘可完成全部操作；无"必须 hover 才能知道"的信息
- [ ] **U8 状态语义**：状态用游戏语义表达；"不可用"能表达出缺什么，而不只是变灰
- [ ] **U9 可读性**：在目标逻辑分辨率下最小字号可读；关键数值除颜色外有第二重编码（形状/符号/位置），不依赖颜色单通道
- [ ] **U10 反馈不静默**：任何数值/状态变化在 400ms 内有可见反馈
- [ ] **U11 一致性（Degree not Kind）**：与已有面板/HUD 并排看像"同一台设备"；复用共享样式层而非新造一套基元
- [ ] **U12 有参考锚点**：能说出 2-3 个具名游戏参考，且产出与参考并排不违和
