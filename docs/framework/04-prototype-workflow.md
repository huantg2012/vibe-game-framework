# 阶段3: Prototype（原型）

## 目标

用最少代码验证一个问题：**核心玩法有趣吗？**

不追求代码质量、视觉效果、完整功能。只追求"跑起来能玩，玩了能感受到核心体验"。

**输入**：GDD + 技术架构方案
**输出**：可运行的核心玩法原型 + 验证结论（fun or not fun, 为什么）

---

## 本阶段的节奏

原型阶段是高频次、短循环的 vibe coding：

```
每个循环 15-60 分钟：
  你描述要什么 → AI生成代码 → 跑起来 → 你试玩 → 反馈调整
```

目标是一天内完成第一个可玩版本，然后用 3-7 天迭代到"好玩"或"确认不好玩需要改方向"。

---

## 子步骤

```
Step 1: 项目脚手架    →  技术环境跑通
Step 2: 核心机制实现  →  最小可交互版本
Step 3: 循环闭合      →  能完成一次完整的核心循环
Step 4: Playtest      →  自己玩 + 让人玩 + 记录感受
Step 5: 迭代/转向     →  基于验证结果调整或推进
```

---

## Step 1: 项目脚手架

### 你做什么

- 确认 AI 生成的项目结构跑得起来
- `npm run dev` 能启动，浏览器能看到东西

### AI Agent 做什么

**角色：Code Agent（脚手架模式）**

一次性生成完整的项目初始结构：
- package.json + 依赖
- Vite 配置
- 目录结构（按 architecture.md）
- 入口文件 + 游戏循环骨架
- 一个能显示的空场景

### Prompt 策略

```
请根据以下技术架构初始化项目：
[粘贴 architecture.md 的技术选型和目录结构部分]

要求：
1. 生成完整的项目文件（不是片段）
2. npm install + npm run dev 能直接跑
3. 浏览器打开能看到一个[游戏画布/空场景/占位画面]
4. 游戏主循环骨架已搭好（update + render）
5. 不要加任何游戏逻辑，只是空壳

这是第一步，我需要确认技术栈能跑通。
```

### 验收标准

- [ ] `npm run dev` 无报错
- [ ] 浏览器显示游戏画布
- [ ] 热更新有效（改代码自动刷新）
- [ ] 目录结构符合 architecture.md

## Step 2: 核心机制实现

### 你做什么

- 将核心机制 spec 拆成小块，每次给 AI 一块
- 每块完成后立刻跑起来看效果
- 用"感觉对不对"来引导方向

### AI Agent 做什么

**角色：Code Agent（实现模式）**

逐块实现核心机制：
- 每次只做一个小功能点
- 保证每次提交后项目仍可运行
- 用简单占位代替暂不需要的部分（方块代替角色图等）

### 任务拆分原则

将系统 spec 拆成"每块15-30分钟能完成"的单元：

```
示例：一个回合制战斗系统

单元1: 显示两个方块代表敌我 + 血条
单元2: 点击"攻击"按钮，对方扣血
单元3: 敌方自动回击
单元4: 血量归零判定胜负
单元5: 加入技能选择
...
```

### Prompt 策略（逐块实现）

```
当前项目状态：[简述已有的功能]
本次任务：[一个具体的小功能]

系统设计参考：
[粘贴相关 spec 中的规则/状态模型段落]

要求：
1. 实现这个功能
2. 保持现有功能不受影响
3. 用最简单的方式实现（占位图、简单动画即可）
4. 完成后项目能直接运行看效果
```

### Prompt 策略（修正调整）

```
我刚试了一下，问题是：[描述你看到/感觉到的问题]
我期望的效果是：[描述期望]

请调整。不要重写整个文件，只改需要改的部分。
```

## Step 3: 循环闭合

### 你做什么

- 从头到尾走一遍核心循环，检查是否自洽
- 记录"断裂点"（循环中无法继续的地方）

### AI Agent 做什么

**角色：Code Agent（整合模式）**

- 连接各个独立实现的机制，形成完整循环
- 补充循环中缺失的过渡（状态转换、画面切换）
- 确保"一轮游戏"能从头玩到尾

### 产出

一个可以"玩一局"的版本，即使粗糙但能体验到核心循环。

### Prompt 策略

```
现在各个机制已经独立实现了：
- [机制A]: 能工作
- [机制B]: 能工作
- [机制C]: 能工作

但它们还没有串起来。核心循环应该是：
[粘贴核心循环描述]

请帮我将它们连接起来，使玩家能完成一次完整的循环：
[起始状态] → [机制A] → [过渡] → [机制B] → [结算] → [回到起始]

补充缺失的过渡逻辑和状态管理。
```

## Step 4: Playtest（试玩验证）

### 你做什么

这步**完全是人的工作**，AI 不参与试玩判断：

1. 自己玩至少 10 次完整循环
2. 找 1-2 个人试玩（发链接即可，Web 游戏的优势）
3. 记录感受，诚实回答：
   - 核心体验出现了吗？
   - 哪个瞬间最接近目标体验？
   - 哪里无聊/困惑/沮丧？
   - 10次循环后还想继续玩吗？

### AI Agent 做什么

**角色：分析助手（试玩后）**

- 帮你整理试玩笔记为结构化反馈
- 基于反馈提出可能的原因分析
- 建议调整方向（但你做决定）

### 产出

```markdown
## Playtest 记录

### 基本信息
- 版本：[commit hash/日期]
- 试玩人数：[N]
- 每人时长：[约X分钟]

### 核心体验验证
- 目标体验出现了吗？ [是/部分/否]
- 最接近目标体验的瞬间：[描述]
- 最偏离目标体验的瞬间：[描述]

### 问题清单
| 优先级 | 问题 | 可能原因 | 建议调整 |
| ------ | ---- | -------- | -------- |
| P0 | [阻断性问题] | [原因] | [方案] |
| P1 | [体验问题] | [原因] | [方案] |
| P2 | [小问题] | [原因] | [方案] |

### 结论
- [ ] 核心有趣，继续推进（→ Production）
- [ ] 方向对但需要调整机制（→ 迭代）
- [ ] 核心不 work，需要转向（→ 回到 Ideation/Design）
```

## Step 5: 迭代/转向

### 路径 A：核心验证通过 → 进入 Production

- 将原型代码打 tag（`prototype-validated`）
- 决定：原型代码是否保留还是重写
  - 保留：直接在上面继续开发（快但可能欠技术债）
  - 重写：用原型验证的设计重新搭架子（慢但干净）
  - 建议：大多数情况保留，局部重构

### 路径 B：需要迭代 → 重复 Step 2-4

- 基于试玩反馈修改设计
- 再次实现 → 试玩 → 验证
- 最多 3 轮，如果 3 轮后仍然 not fun，走路径 C

### 路径 C：核心不 work → 转向

- 不是失败，是正常的验证结果
- 回到 Ideation 或 Design 调整核心机制
- 原型代码中可能有可复用的部分（框架、工具函数）

## 本阶段的 Agent 配置

原型阶段回到**单会话高频交互**模式：

| 模式 | 说明 |
| ---- | ---- |
| 一个 Claude Code 会话 | 整个原型阶段可以在一个长会话中完成 |
| 角色 = Code Agent | 主要就是写代码和改代码 |
| 节奏 = 15-30分钟/轮 | 每轮一个小功能，立刻验证 |
| 上下文管理 | 项目小（原型通常 <2000 行），单会话够用 |

### 会话中途如果上下文不够了

当项目变大或会话变长：
1. 开新会话
2. AI 先读 CLAUDE.md + 相关源文件
3. 告诉它"继续实现 [xxx]"
4. 无缝衔接

---

## Vibe Coding 在原型阶段的最佳实践

### DO

- 每次只描述一个小变化
- 用"我想看到..."开头描述期望效果
- 立刻运行、立刻反馈
- 允许丑陋的代码（原型的目的是验证，不是优雅）
- 频繁 commit（每完成一个可用状态就 commit）

### DON'T

- 不要一次描述 5 个功能让 AI 全做
- 不要纠结代码质量（原型阶段）
- 不要加"以后可能需要"的功能
- 不要在没跑起来的情况下继续加新功能
- 不要跳过试玩就宣布原型完成

---

## 质量门禁：Prototype → Production

- [ ] 核心循环可玩且有趣（主观但诚实的判断）
- [ ] 至少 1 人以外的人试玩过并给了反馈
- [ ] 清晰知道"有趣在哪"和"问题在哪"
- [ ] 已决定：保留原型代码 vs 重写
- [ ] 已更新 GDD（基于原型验证的调整）
