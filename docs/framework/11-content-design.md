# 内容设计与管理

## 概念区分

游戏的"设计"有两层：

```
System（系统）= "物品系统怎么运作"
  ↕ 定义了
Schema（数据结构）= "一个物品有：名称、类型、稀有度、属性{}"
  ↕ 填充了
Content（内容）= "铁剑：武器，普通，攻击力10"
```

当前框架的 `docs/specs/system-*.md` 覆盖了 System 层。本文档补充 Schema 和 Content 层。

---

## 框架增强：Content Spec

### 什么是 Content Spec

Content Spec 是**一个系统内所有具体条目的设计文档**。它包含：
- 该系统的内容 schema（从 system spec 派生的数据结构）
- 所有已设计的条目及其完整属性
- 条目间的关联关系
- 平衡意图（为什么数值是这样的）

### 文件组织

```
docs/
├── specs/
│   ├── system-combat.md       ← 系统如何运作（规则）
│   ├── system-items.md        ← 物品系统如何运作（规则）
│   └── system-skills.md       ← 技能系统如何运作（规则）
├── content/
│   ├── enemies.md             ← 所有敌人的条目设计
│   ├── items.md               ← 所有物品的条目设计
│   ├── skills.md              ← 所有技能的条目设计
│   ├── levels.md              ← 所有关卡的条目设计
│   ├── progression.md         ← 进度曲线（等级表、解锁顺序）
│   └── economy.md             ← 经济平衡（产出/消耗/价格体系）
```

### System Spec 与 Content Spec 的关系

```
system-items.md 定义：
  "一个物品由以下字段组成：id, name, type, rarity, stats{}, flavor_text"
  "稀有度分为：common/rare/epic/legendary，系数 1.0/1.5/2.0/3.0"
  "物品可通过：商店购买、敌人掉落、制作获得"

content/items.md 填充：
  "ITM_001: 铁剑, weapon, common, {atk: 10}"
  "ITM_002: 水晶刃, weapon, rare, {atk: 15, magic: 5}"
  ...
```

System Spec 由 Design Agent 在设计该系统时创建。
Content Spec 由 Design Agent 在后续 Slice 中逐步填充。

## Content Spec 格式

```markdown
# 内容设计：[内容类型名]

## Schema（来源：docs/specs/system-[name].md）
[简要列出该类型的数据结构，或引用 system spec]

| 字段 | 类型 | 说明 | 约束 |
| ---- | ---- | ---- | ---- |
| id | string | 唯一标识 | 格式: [前缀]_[序号] |
| name | string | 显示名 | 使用 world.md 术语表 |
| ... | ... | ... | ... |

## 条目列表

### [分组1]（如：武器）

| id | name | [关键属性] | [关键属性] | 设计意图 | 来源 Slice |
| -- | ---- | ---------- | ---------- | -------- | ---------- |
| ITM_001 | 铁剑 | ATK: 10 | common | 初始武器，基准线 | Slice 2 |
| ITM_002 | 水晶刃 | ATK: 15, MAG: 5 | rare | 第一个魔法混合武器 | Slice 3 |

### [分组2]（如：消耗品）
...

## 关联引用

[本内容引用了哪些其他内容]
| 本条目 | 引用类型 | 引用目标 | 说明 |
| ------ | -------- | -------- | ---- |
| ITM_002 | 制作材料 | ITM_010, ITM_011 | 需要水晶+铁矿 |
| ITM_003 | 技能消耗 | SKL_005 | 被"火焰箭"消耗 |

## 平衡备注

[设计意图和数值逻辑]
- 基准线：[xxx 是数值 1.0 的标准]
- 成长曲线：[每级/每稀有度 增幅多少]
- 已知的待调整项：[什么数值存疑，需要 playtest 后确认]
```

## 内容的生命周期

### 在 Slice 中的位置

内容设计嵌入在正常的 Slice 流程中：

```
系统 Slice（如 Slice 2: 物品系统）：
  1. Design agent 设计系统规则 → system-items.md
  2. Design agent 同时定义 schema + 首批内容条目 → content/items.md（初版，几个条目够测试）
  3. Code agent 实现系统
  4. QA 验收

内容 Slice（如 Slice 5: 物品扩充）：
  1. Design agent 设计新一批条目 → 追加到 content/items.md
  2. 平衡检查：新条目和已有条目是否数值合理
  3. Code agent 填充数据文件
  4. QA 验证数据格式正确 + 游戏内表现符合预期
```

### 内容的增长策略

1. **系统 Slice 时**：只设计 3-5 个条目，够验证系统可用
2. **专门的内容 Slice**：批量设计 10-20 个条目，填充游戏丰富度
3. **Polish 阶段**：平衡调整已有条目的数值

## 关联引用管理

### 为什么重要

游戏内容形成网络：
- 技能 A 消耗物品 B
- 敌人 C 掉落物品 D
- 关卡 E 的 boss 是敌人 F
- 成就 G 要求完成关卡 E

如果删除/修改物品 B，技能 A 就坏了。

### 管理方式

1. **Content Spec 中的关联引用表**：每个条目列出它引用了什么
2. **QA 验收时检查**：修改/删除条目时，QA 搜索所有 content spec 中对该 ID 的引用
3. **Code 层面**：数据文件中使用 ID 引用（不硬编码），便于搜索

### 变更影响分析

当修改一个内容条目时：
```
1. 在所有 content/*.md 中搜索该条目的 ID
2. 找出所有引用方
3. 评估影响
4. 更新所有受影响的条目
```

这正是"变更传播"原则在内容层面的应用。

## 数值平衡

### 谁负责

- **Design Agent**：设计平衡意图（基准线、成长曲线、相对强度）
- **人**：通过 playtest 判断"感觉对不对"
- **QA Agent**：检查数据是否符合设计意图（如"rare 物品应该是 common 的 1.5 倍"）

### 平衡不是一次性的

平衡随内容增长而迭代：
- Slice 2（物品系统上线）：3 个物品，手动平衡
- Slice 5（物品扩充）：20 个物品，需要系统性检查曲线
- Polish：最终调整，基于玩家反馈

Design Agent 在设计内容条目时，必须在 content spec 中标注**平衡备注**：为什么这个数值是这样的，基准线是什么。

## 进度曲线设计

### 特殊性

进度曲线（什么时候获得什么、难度如何递增、解锁顺序）是一个**跨系统**的设计关注点——它不属于任何单一系统，而是连接多个系统：

- 等级表连接经验系统和属性成长
- 解锁顺序连接关卡进度和技能/物品获取
- 难度曲线连接敌人强度和玩家预期实力

### 文件位置

`docs/content/progression.md` — 独立的内容设计文档，跨系统引用。

### 格式

```markdown
# 进度曲线设计

## 核心节奏
[玩家从 0 到终点的体验节奏描述]

## 时间线

| 阶段 | 游玩时长 | 玩家获得 | 面对的挑战 | 核心感受 |
| ---- | -------- | -------- | ---------- | -------- |
| 开局 | 0-10min | 基础攻击 | 弱敌 | 学习操作 |
| 前期 | 10-30min | 第一个技能 + 首把武器 | 中等敌人 | 发现成长感 |
| ... | ... | ... | ... | ... |

## 解锁序列
[按时间顺序，什么时候给玩家什么]

## 难度曲线
[玩家实力 vs 挑战强度的关系]
```

## 量产机制

### 从"少量测试"到"批量生产"

当内容需要从几个扩展到几十个时：

1. **标杆法**：手动打磨 2-3 个标杆条目（Design Agent 仔细设计）
2. **模板提取**：从标杆中提取规律和变化维度
3. **批量生成**：Design Agent 按模板批量设计变体
4. **人审核**：筛选、调整、淘汰不合适的
5. **实现**：Code Agent 批量填入数据文件

### AI 批量生成内容时的约束

Design Agent 批量生成内容条目时，必须受以下约束：
- system spec 中定义的 schema（格式正确）
- world.md 中的设定规则（叙事合理）
- 已有条目的平衡基准线（数值合理）
- 不与已有条目重复或过于相似

## 对现有框架的影响

### 不需要新增 Agent

内容设计是 Design Agent 的自然延伸：
- 系统设计 → 产出 `docs/specs/system-*.md`
- 内容设计 → 产出 `docs/content/*.md`

同一个 Agent，不同的输出格式。

### 需要扩展的

1. **Design Agent**：增加"内容设计"模式，知道 Content Spec 格式
2. **QA Agent**：验收时增加"关联引用检查"
3. **Director**：Slice 规划时能区分"系统 Slice"和"内容 Slice"
4. **文档结构**：新增 `docs/content/` 目录

### Slice 类型扩展

从"一种 Slice"变为可以识别不同性质的 Slice：

| Slice 类型 | 特征 | 示例 |
| ---------- | ---- | ---- |
| 系统 Slice | 新增一个系统（规则+代码+少量测试内容） | "实现物品系统" |
| 内容 Slice | 在已有系统内批量生产内容 | "设计20个新敌人" |
| 功能 Slice | 扩展已有系统的功能 | "给物品系统加制作功能" |
| 集成 Slice | 连接多个已有系统 | "战利品掉落连接战斗+物品" |
| 打磨 Slice | 优化已有功能的体验 | "战斗打击感优化" |
