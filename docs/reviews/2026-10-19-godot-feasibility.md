# Godot 迁移可行性与必要性评估

日期：2026-10-19。基线：`027641fe`，独立未提交的 `CLAUDE.md` 不属于本审查改动。目标由用户明确为 **PC 买断发行（Steam 等）**。

范围：维护、画面生产、性能与发行。关联 COH-F005/F007/F012/F039/F042/F044。知情源码审查、两路独立代码核查、现有 QA 与 Godot/Valve/Phaser 官方资料；没有运行 Godot 对照版本，没有新测游戏性能或审美，不宣布已证明迁移收益。仅评估，不授权或启动迁移。现状索引全量 check 在本轮被有界中止，不能声称全库登记检查通过；相关事实另按实际源码和近期 QA 核验。

> **评估后的用户决定（2026-10-19）：迁移计划搁置。** 保留本报告的技术结论，暂停全面迁移及建议的单场景试迁；继续当前栈，开发重心转回核心玩法。下文建议是评估结果，不再作为待执行任务。

## 判断

**技术上可行；对 PC 正式版有较强的长期价值；现在没有必须立即全面迁移的证据。建议将 Godot 作为目标运行时候选，先做小范围、可退出的实迁验证，通过后再分阶段切换。**

最强理由是减少长期需要自行维护的平台与呈现接线，以及建立原生 PC 发行流程。画面自动变好、生成自动变快、AI token 自动减少，都不是成立的迁移理由。

目前只有三个开放世界，是控制验证规模的好机会；但净化点、完整物品/成长、菜单、存档和跨场景事务仍须迁移，不能把它理解为移植三个小样例。

## 1. 当前栈与迁移边界

项目是 TypeScript/Vite/Phaser 3，加自有 WebGL2 材质与光照、Canvas 像素处理、DOM/CSS UI、生成与表面准备 Worker；依赖中还有 Three，部分属于历史/DEV路径，不能视为当前 Rift 使用完整 Three 场景。正式固定逻辑分辨率为960×640。

按路径和生成标记粗分，`src` 普通源约9.32万行，另有DEV/Gym约2.55万、生成数据约11.91万、冻结历史执行器约170.55万。普通源仍包括程序美术和保留模块，**这些不是精确迁移工作量，更不能把历史生成文件总行数当重写量**。

- **保留内容与制作投资**：CSV、玩法合同、世界构型设计、PNG/音频、图集数据及既有测试案例；Node 制作工具可继续离线运行。素材的采样、颜色空间和元数据需重新核验。
- **转译并对照**：库存/成长/归返事务、AI、生成算法、视野/碰撞、随机序列。纯 TS 边界有助迁移，不意味着 Godot 可直接执行这些模块。
- **重新实现接线**：场景生命周期、输入与相机、全部 DOM 界面、音频封装、Worker/取消链、文件存储、WebGL 资源与着色器入口。

证据：[配置](../../src/config/game-config.ts)、[库存](../../src/systems/inventory-store.ts)、[保存](../../src/managers/save-manager.ts)、[DOM](../../src/ui/dom/panel-styles.ts)、[架构](../architecture.md)。

## 2. 维护：长期潜在收益明显，短期成本高

Godot 提供统一的场景、资源、动画、输入、UI、音频和调试工具，适合减少现在多个生命周期与坐标体系间的接线。未来设计者直接调整场景、动画与参数，也比持续为每种操作制作独立网页练习场更有复用潜力。[官方能力](https://docs.godotengine.org/en/stable/about/list_of_features.html)

但本项目主要由 AI 进行文本生产，不能把“有可视编辑器”直接计作效率提升。Godot 支持命令行导入、无窗口运行和发布构建，仍可保持 CSV→代码/资源、自动验证、文本审查的流程；需要建立对应测试入口，现有浏览器脚本不能全部照搬。[命令行](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

迁移要真正移除重复的平台代码，而非把自制渲染器、DOM桥和双运行时原封不动包进去。Godot 不会自动解决超大场景类、无界生成搜索、历史兼容包增长或验收范围不清的问题。

对 PC 优先的本项目，我倾向试验 **Godot 4 .NET/C# 承载核心规则，Godot 节点负责场景与呈现，原 Node 工具继续离线生产 CSV 对应资源**。保留静态类型和纯逻辑测试边界；不为保住 TS 而增加非官方脚本运行时。C# 不是性能保证，也需避免每像素跨引擎 API 调用。若未来把网页试玩重新列为硬目标，应重新选择语言：目前 Godot 4 C# 仍不能导出 Web。[官方语言范围](https://docs.godotengine.org/en/stable/about/faq.html)、[Web 限制](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

**维护判断：有条件改善。** 短期必然增加一套实现与回归成本；长期是否节省工时/token，须通过同一类小改动的完成成本比较，不能预报百分比。

## 3. 画面：能保留风格，更容易组织动态，不是自动升级

本项目值得保留的是固定视角的像素轮廓、材料差异、肩灯、空间空洞、角色同场受光和净化点的分层纵深。Godot 的2D精灵、法线受光、遮挡、粒子与 shader 足以承载相应制作路线；迁移不要求把已认可的2D Rift改成完整3D。[2D灯光](https://docs.godotengine.org/en/stable/tutorials/2d/2d_lights_and_shadows.html)

主要收益是把动画、灯、特效和资源组织放入同一环境，降低之后制作动态效果和调整时序的接线成本。当前造型、材质与构型成果不应为了迁引擎重画。

最难的是**保真重建**：Rift有高度/法线/AO等材质场、VOID光传播规则和角色逐像素受光；净化点有深度分层、体积核心及肩灯阴影。普通 Light2D 不能直接替代这些语义。既有 GLSL 的数学可复用，但接口、混合、纹理格式、坐标、透明度、颜色空间都须适配。[shader迁移](https://docs.godotengine.org/en/stable/tutorials/shaders/converting_glsl_to_godot_shaders.html)、[当前净化点管线](../architecture.md)

尤其必须把**玩法视野**和**视觉灯光**分开：VOID阻行遮视且不可照亮，普通实体只阻身体/近战，不能因为统一使用引擎阴影而改掉规则。像素硬边、最近邻采样、整数缩放和字体层级也需要显式配置。

**画面判断：可保持且有扩展空间；自动提升不成立。** 初期最大风险是看似效果更丰富，却丢掉已有画面身份或可读性。本轮没有 Godot 实帧，不能给审美通过。

## 4. 性能：有架构优化机会，尚无引擎优劣实测

2026-10-18同一轮三图中污染记录：余烬脊8.123秒、晶化林床7.586秒、破膜盆地16.088秒入场。限定流程功能通过，但50ms连续任务预算仍未通过。不是稳态FPS，不是GPU时间，也不是目标Windows硬件的发行认证。[原汇总](../qa/artifacts/three-world-pool-2026-10-18/browser-summary.json)、[QA范围](../qa/three-world-pool-2026-10-18.md)

源码显示三类值得测量的成本：

1. **入场 CPU 与上传**：生成、准入、内容重试、四张RGBA烘焙、主线程重建及纹理上传。改成GDScript/C#不能自动消掉搜索复杂度；已认可固定构型可以评估更多离线预计算，动态内容仍可运行时生成。
2. **帧内 GPU/提交**：独立WebGL2按整张地图大小着色，再将结果交给Phaser纹理。统一GPU资源、按视口/区块工作可能减少成本；仍须剖析才能确认占比。[地表renderer](../../src/systems/r100-world/surface-renderer.ts)、[提交](../../src/systems/r100-world/presentation.ts)
3. **角色帧内 CPU**：A人物及本土类人有逐像素受光和纹理更新。将合适部分放入shader可能有收益；把循环逐行翻成脚本则可能没有收益甚至退步。[A人物](../../src/entities/player-last-light-presentation.ts)、[类人](../../src/entities/form-renderers/d/model-visual.ts)

这三类优化中，部分在现有栈也可实现。必须比较“Godot重构”与“现栈定向优化”，而非把算法改进全记到换引擎头上。Godot同样要求先定位CPU/GPU瓶颈；原生运行时不免除过度绘制、纹理带宽和分配成本。[CPU优化](https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html)

**性能判断：改善潜力合理，但具体收益未知。** 50ms长任务门与60FPS所需约16.7ms帧间隔是两个指标，后续须分别测量加载、帧分布、CPU/GPU与内存。

## 5. 发行：与PC目标匹配，是最明确的迁移动机

Godot提供Windows/macOS/Linux导出与原生文件、窗口、输入路径。MIT许可允许商业发布；仍须保留所需许可声明。相对新增并维护浏览器桌面壳，运行时和发布工具更集中。[平台与许可](https://docs.godotengine.org/en/stable/about/faq.html)

但 **Steam不要求使用Godot**。现栈可以走Electron等桌面封装，Phaser官方已有该发行路径；这是保留现有代码、较快形成PC试玩包的真实备选，不代表已替本项目验证。[Phaser官方发行案例](https://phaser.io/news/2025/03/publishing-web-games-on-steam-with-electron)

成就、Steam Overlay和云存档策略仍须接入/配置/验证；Steamworks API甚至不是上架的强制条件。更换引擎不替代手柄交互、分辨率/全屏、音量、崩溃日志、安装更新、目标硬件测试和商店交付。[Valve说明](https://partner.steamgames.com/doc/sdk/api)

若以后上主机，Godot仍需平台批准及自建/第三方移植支持，并非官方一键导出。本次PC目标无需为潜在主机扩展提前付费或增加范围。[主机支持](https://godotengine.org/consoles/)

**发行判断：Godot更贴合长期PC产品组织；不是能否上架的分水岭。** 若短期目标是尽快发一份试玩包，现栈封装往往范围更小；若继续多年扩充、维护，原生底座的价值更大。准确成本仍待样本。

## 6. 建议的验证与决策

采用查询时已发布稳定版4.7.2作为候选，冻结引擎/插件版本；4.8仍在beta，不拿未来版本承诺当能力依据。[官方归档](https://godotengine.org/download/archive/)

**第一关：最难的画面片段。** 固定破膜盆地一份实际配方，包含A人物、类人、菌毯、地表、VOID及灯光；另取净化点一段含坡道/前后遮挡/肩灯的片段。先复用相同输入隔离生成差异。比较同机同分辨率、同路线的发布构建（现栈用生产构建，非Vite热更新），记录CPU/GPU、帧p95/p99、启动、内存。画面身份/规则不退步；针对目标硬件拟定60FPS及加载预算后判断收益，不能凭FPS平均值通过。

**第二关：完整小循环。** 只迁一张Rift及必要净化点功能，走备行→搜取/遭遇→撤离或死亡→归返→保存/冷续。单独恢复真实生成/准备，避免用预烘焙绕过成本后声称加载变快。再做同一类玩法/视觉小改动，比较所需修改点、验证成本与回归数。

通过后再迁另外两图和剩余系统，并删除被取代的运行时接线；不长期双栈同步开发，不同时扩108世界或重设计玩法。没有通过时停止扩迁，保留试验结论，继续现栈的定向优化和PC封装。

旧档策略须在实施前单独确定。上次授权只处理被关闭世界的废局，不等于允许本次清空三图有效局或基地进度。建议评估迁移必要基地数据、为新运行时建立明确版本边界；不默认移植全部冻结历史执行器，也不未经授权丢档。

**最终结论：对这个以Steam等PC买断为目标、仍在重构和完善中的项目，我倾向有条件转向Godot。先验证保真、性能与实际维护收益，再批准全面迁移。发行和长期维护是主要收益，短期全面重写的必要性不足。** 本报告不是迁移任务，未更改玩法、引擎或既有挂起状态；不承诺未经样本支持的工期和token节省比例。
