# UX 参考研究：为什么是这几个游戏

> **声明**：本文件是研究性材料，供设计判断使用，**不是可直接引用的规范条目**。任何 ui spec 需要"参考锚点"时，应引用本文件的论证结论，但具体视觉数值以 `ui-art-overhaul.md` v2 为准。

## 0. 为什么不能闭门造车

`guides/99-review.md` FV-01 记录的事实：Slice 4.5 表现层翻修花了七轮人工返工，唯一让方向收敛的输入是人给出的具名游戏参考。没有参考锚点时，语言模型的默认先验是通用 web 界面——圆角卡片、渐变按钮、hover 提示、居中弹窗。这不是审美判断错误，是**先验分布错误**：训练数据里"UI"的最大概率簇是 SaaS 后台，不是游戏。

本文件的任务不是列一份"像素游戏 UI 灵感清单"，而是针对本项目的具体气质——**孤独的仪式性维护、工业/终端质感、裂隙内的潜行压力、资源分配的纠结、缓慢的绝望**——逐一论证"为什么是这个参考"和"学什么、不学什么"。抄错参考比不抄更贵：一个视觉上很像但方法论不通的参考（比如抄了 Hollow Knight 的图标风格却没学到它的信息节制）只会把风格拉过去、把体验拉歪。

## 1. 选定参考与论证

### 1.1 Signalis —— 世界内终端的物理真实感

**为什么选它**：本项目的 art-direction.md 已经用 Signalis 锚定过视觉质感（low-fi 像素、受限色调、工业质感 UI），但那是"画面长什么样"。这里要锚定的是它UI 层更进一步的东西：**Signalis 里的每一屏信息（物品检视、日志阅读、地图）都以"这是角色手上那台设备/那本笔记的物理内容"的方式呈现**——检视物品時屏幕真的像被一台扫描仪读出，字体、扫描线、轻微色差全部服务于"这是世界里一台真实存在的机器"，而不是"游侧的说明浮层"。

**学什么**：
- 检视/详情信息的呈现方式是"设备读出结果"，不是"浮动 tooltip"——这直接解决本项目 title 属性 tooltip 的载体错误问题。
- 扫描线、色差等做旧手法可以是**结构性**的（提示"这是一块老旧屏幕"），不是纯装饰。
- 受限色调下，信息层级完全靠亮度差建立，不靠加色相。

**不学什么**：
- 不学它的解谜式物品组合玩法（与本项目机制无关）。
- 不学它偏"复古 CRT 圆角显像管"的曲面畸变滤镜——本项目的美术方向是"勉强维持的工业残骸"而非"旧式家用电器"，画面畸变会喧宾夺主，且与像素风的锐利像素矛盾（`art-direction.md` 明确 `pixelArt: true` 要保持像素锐利）。

### 1.2 FTL: Faster Than Light —— 资源分配 HUD 的语言

**为什么选它**：本项目最核心的决策压力是资源分配（薪柴分给哪个模块、装备哪几件工具/防御品），这与 FTL 的"给哪个子系统供电"是同构问题。FTL 用一条系统条形（子系统名 + 血条 + 供电格）就让玩家在几秒内完成决策，且全程无 hover-only 信息、无弹窗打断战斗。

**学什么**：
- 一个资源槽位 = 名称 + 数量/容量条 + 状态色，三者同屏,不需要点开才知道。这直接对应本项目净化点模块分配面板和裂隙 HUD 工具槽的设计目标——"玩家不看任何文档，能否说清带了什么"。
- 关键决策信息**常驻屏幕边缘**，游戏过程不因为要查状态而暂停/跳出。
- 危险状态（子系统着火/断电）靠**图标+颜色+动画**三重编码，不单靠红色。

**不学什么**：
- 不学它的科幻感全息蓝色配色（与本项目"暖色=人类，冷色=污染"的色彩纪律直接冲突）。
- 不学它的圆形能量格图标——圆形填充仍专门留给「污染体的面积光池」这类叙事专属场景，不能用来做通用 UI 图标。裂隙地面污染现行是崩坏簇（`art-direction.md` §4.2，DEC-069），不是网格对齐矩形平涂；工具范围仍用网格矩形块（DEC-038），不要把地面簇合同套到图标上。

### 1.3 Darkest Dungeon —— 密集词条信息的可读组织

**为什么选它**：本项目的污染物系统已增长到 18 型 × 3 稀有度，且每件都有独立描述文本（`CONTAMINANT_DATA`），这与 Darkest Dungeon 的饰品/怪癖系统（大量独立词条，每条需要玩家在决策瞬间读懂）是同一类信息密度问题。DD 的解法是：图标形状先建立"这是什么大类"的第一印象，颜色/边框建立"品级"，数字建立"程度"，**三层叠加不互相依赖**——玩家可以只看形状快速筛，也可以细读文字确认。

**学什么**：
- 物品格 = 图标/符号（大类）+ 边框色（品级）+ 数字（程度），三层信息独立编码,不是靠一段话堆出来的描述框。
- 状态/减益用**固定位置的小型标记**，不用悬浮气泡糊住主体——这与 `docs/art/tool-vfx-spec.md` 已经锁定的"受影响敌人标示"方法论一致，本文件将其扩展到 UI 层的物品/状态标示。
- 火把亮度（光照资源）作为一条**始终可见、随时影响判断**的资源条，功能等价于本项目的混乱值条——DD 证明了"一条随时看得到的压力条"可以撑起整个决策张力,不需要更多 UI。

**不学什么**：
- 不学它插画卡牌式的角色立绘和叙事旁白框——本项目玩家"无个性、不表现感受"（`world.md`），插画感的角色卡片会立刻违反这条设定。
- 不学它的羊皮纸/哥特花纹边框装饰——纯装饰边框在本项目是"后台管理系统"式的过度装饰,直接违反 U2。

### 1.4 Into the Breach —— 威胁预告的网格化诚实

**为什么选它**：本项目的冲击预警（下一轮打谁、多重）和 `tool-vfx-spec.md` 已经用 Into the Breach 锚定了 VFX 的形状语言（网格对齐矩形块，不用圆形光晕）。这里把同一个锚点扩展到 UI 层的**预告信息可信度**问题——ItB 的核心信任机制是"预告的伤害数字和范围 100% 精确，从不撒谎",玩家的每个决策都建立在这份可信之上。

**学什么**：
- 预告信息（冲击强度、目标模块）用**同一套符号语言**贯穿"预告-发生-结算"三个阶段,不要预告时是文字、结算时是另一套图表——本项目 `purification-hud.ts` 的模块图标+ pip 条已经在这么做,这个方向要在 v2 里保持并扩展到其他预告场景。
- 数值预告优先**离散、可数的符号**（格子/pip）而不是连续渐变条,离散符号更容易在快速决策中被精确读出。

**不学什么**：
- 不学它的战棋网格叠加显示（本项目不是战棋,没有可点击网格）。
- 不学它高饱和度的霓虏色 UI 边框——与本项目冷灰工业基调不符。

### 1.5 Barotrauma —— 设备读数与警报的世界内诚实感

**为什么选它**：净化点模块（CORE/STORAGE）的健康度、冲击时的告警,本质是"一套勉强维持的机械系统正在承压",这正是 Barotrauma 潜艇反应堆/泵站系统的核心体验。Barotrauma 的系统读数是**物理仪表盘**——指针、刻度、警示灯,坏掉时是指针乱转/警示灯闪烁,不是弹出一个"系统错误"对话框。

**学什么**：
- 系统健康度用"这台设备本身在告诉你状态"的方式呈现（指示灯颜色/闪烁频率）,而不是抽象进度条+文字标签的组合——本项目 `purification-module.ts` 三态指示灯已经是这个方向,v2 要把这个诚实感从模块本体延伸到 HUD 摘要层。
- 警报是**世界内事件**（警铃声+灯光变化）,不是浮层通知——这与本项目"反馈不静默但不能是 web toast"的要求一致。

**不学什么**：
- 不学它高度拟真的仪表指针/阀门轮这类具体机械形态——本项目分辨率是 32px 像素级,精细指针刻度会糊成一团,且与本项目"低细节密度、看不清比看清更有效"的美术原则冲突（`art-direction.md` §1.2）。只借用"设备读数即状态"的**逻辑**,不借用"仪表盘"的**具体形态**。

## 2. 方法论拆解：这些游戏怎么做到"像游戏"

### 2.1 信息层级：常驻 vs 唤出

以上参考共同的结构是三层信息节奏（与 `docs/specs/_template-ui.md` 的 P0/P1/P2 分级呼应）：

- **P0（始终可见,零操作成本）**：FTL 的系统条、DD 的火把亮度、本项目的混乱值/生命值——这些是"决策瞬间必须已经知道"的信息,一旦需要额外操作（点开/悬停）才能看到,决策链就断了。
- **P1（一个按键/一次走近唤出)**：FTL 点开系统详情、Barotrauma 走到控制台前——需要时主动触发,不常驻画面,但不依赖鼠标 hover。
- **P2（深挖,主动进入某个界面才看到)**：DD 的饰品详细词条、本项目的 `存续报告`/`库存` 面板——信息量大,允许玩家专注阅读,可以暂停游戏节奏。

**本项目的现状问题**：裂隙 HUD 目前把"工具是什么"这个本应是 P0 的信息（每次决策都要用到）做成了 P2 甚至更差——玩家只能在出击前的装备面板看一次,进裂隙后只剩下没有名字的圆点。这是本次重构要修的核心结构性错误（design agent 的 IA 文档会给出准确的 P0/P1/P2 划分,本文件只指出这个方法论）。

### 2.2 世界内载体感怎么营造

**核心手法：材质/字体/边框要能回答"这是哪台机器打出来的字"**。

- Signalis：字体是设备扫描输出的字体,不是游侧说明字体。
- Barotrauma：警报灯的闪烁频率是电路故障的物理结果,不是 UI 设计师加的强调动效。
- 本项目已有的正确案例：`purification-module.ts` 三态指示灯用"熄灭色"表达"设备坏了",这是诚实的载体感。
- 本项目已有的错误案例：`panel-styles.ts` 的 `box-shadow: 0 0 12px rgba(0,0,0,0.6)`——投影/发光是"现代软件的强调手法",不是任何一台工业设备会有的物理效果,这是纯粹的"好看"逃逸到了"像游戏世界的设备"的反面。

**判断标准**：任何一处视觉强调,先问"这个效果对应世界里的什么物理原因",答不出来就是装饰,装饰是 U2 违规的高风险信号。

### 2.3 常驻信息 vs 唤出信息的载体分工

- 常驻信息（P0）几乎全部走**世界内装置/屏幕空间层**（Phaser 层或轻量 DOM 叠加,视觉上是角色随身设备的读数）,因为它必须**不打断**玩家的操作视线。
- 唤出信息（P1/P2）可以走**世界内终端**（DOM 抽屉,视觉上是站在某台设备前操作）,因为这时候玩家已经主动暂停行动来"读设备"。
- 元界面（主菜单）是唯一允许"我知道这是个软件"的地方——但即使这样,文案和质感仍要服务于世界观（不是"选择关卡",是"进入净化点"）。

### 2.4 屏幕空间 vs 世界空间的分工

- **屏幕空间**（跟随摄像机,scrollFactor 0）：玩家自身状态（生命/混乱/工具/薪柴）——这是"你随身设备的读数",天然应该固定在你眼前,不随世界移动。
- **世界空间**（随摄像机移动,固定在世界坐标)：撤离点脉动标记、冲击方向的压力叶（`BoundaryShape`）——这是"世界里正在发生的事",天然应该在它发生的地方。
- **本项目的分工基本正确**（HUD 是屏幕空间,压力叶是世界空间),v2 不改变这个分工,只补齐 HUD 内容的完整度。

### 2.5 状态如何用游戏语义表达

以上所有参考都不用 `default/hover/active/disabled` 描述状态——DD 的装备是"可用/不可用（缺什么材料写清楚）/已装备",FTL 的系统是"运行/受损/离线（为什么离线可查）"。**"不可用"永远要回答"缺什么"**,这不是文案友好度问题,是"世界内设备"和"网页表单"的分界线本身——表单的 disabled 是"你不该按这个",设备的"不可用"是"这个东西现在物理上做不到,原因是……"。

### 2.6 可读性与风格化如何同时成立

参考里没有一个是"越暗越好、越难认越有氛围"——DD 画面整体暗但火把光圈内的关键信息(生命/词条数字)对比度非常高;Signalis 整体低保真但检视文字永远清晰。**风格化压缩的是"装饰细节的丰富度",不是"关键信息的可读性"**。本项目当前把这两者搞反了——`.hint` 用 `#5a5f66` on `#0f1114`（对比度约 2.9:1,详见 `ui-art-overhaul.md` v2 §A1）是"为了氛围牺牲可读性"的典型反例,而这五个参考没有一个会这么做。

## 3. 审美总结：可执行的判断原则

以下每条都要能直接拿来判断一个具体设计"过"还是"不过"，不是形容词堆砌。

1. **常驻信息(P0)不超过 6 项,且每项都能在半秒内读出数值,不需要停留或点开。** 判据：数一数当前场景屏幕上同时常驻显示的独立信息点,超过 6 立即精简或降级为 P1。

2. **任何强调效果必须能回答"这对应世界里的什么物理原因",答不出来就删除。** 判据：投影/发光/渐变/圆角这类效果如果答案是"因为好看",直接判违规(对应 U2)。

3. **"不可用"状态必须书面说明缺什么,不能只靠视觉弱化(变灰/降低透明度)传达原因。** 判据：鼠标/键盘选中一个"不可用"项时,画面上必须有文字或符号指出缺口(资源不足几点/前置条件是什么)。

4. **颜色的使用必须能追溯到四层色彩架构(L1-L4)里的一层,追溯不到就是新色值,需要显式论证或替换。** 判据：给任意一处 UI 用色,问"这是碎片色温/污染色谱/玩家暖光/稀有叙事色里的哪一层",答不出来就要改。

5. **关键数值必须有除颜色外的第二重编码(形状/位置/符号/离散计数),纯色相区分不算数。** 判据：把画面转灰度截图,所有关键判断(危险/安全/可用/不可用)是否仍能读出,读不出就不合格。

6. **信息在被"唤出"之前,必须已经有一个静态、常驻的身份标签,不能只在被选中/悬停时才存在。** 判据：不移动鼠标、不做任何操作,截一张当前画面的图,图里能看出"这是什么"吗？看不出就是过度依赖 hover(对应 U7)。

7. **同一游戏内两个界面并排截图,必须读作"同一台设备的两屏输出",边框粗细/圆角(0)/字体族/间距单位必须一致。** 判据：把裂隙 HUD 和净化点面板的截图拼在一起,能不能一眼看出这是同一个游戏(对应 U11)。

8. **面板/浮层的开启必须由世界内动作触发(走近装置/按下对应键),不能无理由自动弹出或纯粹因为"信息量大了就该有个面板"而新增一层。** 判据：能不能用一句话说清"玩家做了什么动作导致这个面板出现"，说不清就是伪需求。
