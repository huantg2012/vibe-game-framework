# 像素派系：六轴坐标与被锁死的技术栈

**核心命题：技术栈基本是风格坐标的函数，不是先选引擎再选画风。** 在轴上做出选择会连带锁死渲染架构、资产管线、动画方式、字体策略里的若干模块。反过来说，一份自洽的美术方向必须能在六条轴上各指出一个位置——指不出来就是方向还没定完。

「像素风」不是一个风格，是一族风格。用「复古像素」「16-bit 风」这类词描述方向，推不出任何技术约束。

## 什么时候用

- 给新项目定美术方向（与项目 art-direction 配合，不替代它）
- 审查已有美术方向是否自洽（轴之间是否互相打架）
- 反推技术栈：坐标确定后，用文末十二项清单逐项给出答案
- 判断一个参考游戏「能学什么、不能学什么」——先看它和你在哪条轴上不同

## 六条轴

前四条描述**画面**，后两条锁死**技术**。后两条最常被漏掉，而它们对工程量的影响比前四条更大。

### 轴一 · 调色板封闭性

不是「多少色」，是**色板是否封闭**。封闭 = 任意混色都算脱板。

| 位置 | 含义 |
| --- | --- |
| 硬件封闭 | 真机或编译器强制（GB 四阶、NES 全局板 + 每 sprite 三色） |
| 虚拟机封闭 | Fantasy console 人为设定（Pico-8 固定 16 色） |
| 自设封闭 | 无硬件约束但自定一份板并强制执行（Lospec 板、项目锁定 palette 文件） |
| 受控开放 | 有色彩纪律（饱和度上限、强调色配额）但不枚举具体色值 |
| 完全开放 | 任意色 + alpha + shader |

硬件代际（8-bit / 16-bit / 街机 / PC-98）是这条轴的**历史来源**，不是轴本身。现代项目可以自设 16 色而与任何硬件无关。

### 轴二 · 笔法

质感的真正来源，与色数关系不大。

- **硬边平涂** — 色块加硬边界，无中间过渡。最「像素」的那种像素。
- **有序抖动 dithering** — 抖动图案模拟渐变。Amiga / DOS / PC-98 正统，现在也被当复古信号刻意使用。
- **手工抗锯齿** — 曲线与斜线上手放中间色柔化锯齿。商业街机的看家手艺，成本最高。
- **Cluster shading** — 不做线性渐变，用形状不规则的色块簇堆出体积。Amiga demoscene 传统。
- **Painterly** — 软渐变、大量中间色，本质是低分辨率数字绘画。
- **色相偏移 hue shifting** — 明暗不靠单纯加黑加白，靠色相位移（暗部偏冷或偏紫、亮部偏暖）。现代像素最主要的质感分水岭之一。
- **描边 / 选择性描边 / 无描边** — 有描边偏卡通、可读性好；选择性描边只在需要分离处描；无描边靠明度对比分离形体，偏氛围与电影感。

### 轴三 · 视角构成

正侧面横版 / 正俯视 / **3⁄4 俯视（oblique）** / **真等距** / 伪 3D（Mode 7 一类）/ 像素 sprite 立在 3D 场景里。

两个术语坑：游戏里说的「等距 isometric」通常是 **2:1 dimetric**，不是数学意义的等距；3⁄4 俯视是斜投影 oblique，绝大多数 JRPG 与生活模拟在这个位置。

### 轴四 · 生产方式

手绘逐帧 / 3D 渲染降采样 / **骨骼驱动像素贴图** / 程序化生成纹理 / 拍摄或扫描数字化（历史）/ AI 生成加量化后处理。

两条注记：

- 骨骼驱动（Spine、DragonBones、引擎 2D IK）与**轴五直接冲突**：旋转和非整数缩放会把像素揉碎。要用就得接受「pixel-styled 而非 pixel-perfect」，或者把骨骼动画烘成帧再用。
- AI 生成属新兴且有争议的一路：发行平台通常要求披露，协作与外包里要先确认许可与披露口径。不要当作默认可用。

### 轴五 · 像素网格纪律（最容易漏，工程影响最大）

四个独立问题，每个都必须有答案：

1. **像素尺寸是否单一？** world / UI / 文本是否同一 px 大小，还是混合（世界低分辨率、UI 与文字按输出分辨率画）。混合最常见，也最容易看起来脏。
2. **允许非整数缩放吗？** 整数缩放最锐，但窗口尺寸只能取整数倍、其余靠 letterbox；非整数缩放能填满任意窗口，代价是像素边缘发虚。**这是取舍不是对错**——商业作品两边都有，见 [archetypes.md](archetypes.md) 里 Shovel Knight 的选择。
3. **允许亚像素移动与旋转吗？** 禁止 → 位置每帧取整、动画只能整格跳、不能用连续 tween 做形变；允许 → 拿到平滑手感，失去像素网格的稳定。折中是逻辑位置连续、渲染时取整，或用 shader 做亚像素滚动。
4. **低分辨率 render target 整数放大，还是高分辨率直接画？** 前者是「真像素」，全屏后处理天然发生在像素分辨率上；后者是「pixel-styled」，能混排高分辨率文本与特效。

### 轴六 · 后处理签名

正交于以上全部——任何坐标都能加或不加：CRT / 扫描线 / 荫罩、bloom、色差、暗角、palette LUT 映射、屏幕空间抖动、景深与 tilt-shift。

关键技术问题不是「加不加」，而是**在哪一级加**。在像素分辨率上加，效果参与像素网格；在输出分辨率上加，会在像素块之上再叠一层不同粒度的纹理。1-bit 抖动的锚定难题（图案锚屏幕空间会随镜头游动，锚世界空间会破坏图案规整）是这条轴的极端案例。

## 定位本项目（先读，再判断）

4. 资产规格（若有）：`docs/art/` 下的 asset-specs 或等价文件
5. 项目已锁定的参考锚点（若有）

产出一行坐标，六个位置全填：`轴一 / 轴二 / 轴三 / 轴四 / 轴五 / 轴六`。

**任何一条指不出位置 = 美术方向还没定完，不要开始画。**

## 锁定关系（选了左边，右边就不再是自由选项）

这是六轴框架真正的用处。轴并非自由组合。

| 一旦选了 | 就同时决定了 |
| --- | --- |
| 封闭色板 | 排斥任意动态光照——混色即脱板。明暗必须烤进美术，运行时合法的变色手段只剩 palette swap 与抖动 |
| 无描边 painterly | 形体分离只剩明度对比一条路，因此**反而必须**有动态光照或强背景压暗，否则角色糊进背景。这与封闭色板的需求方向相反，两者难以共存 |
| 真等距 | 方向变体从 8 起步，手绘成本按方向数线性上升。历史上这一派几乎全部走 3D 预渲染，是算术不是偷懒 |
| 3D 渲染降采样 | 帧数与方向都变便宜，代价是需要 3D 美术岗加一条自动化渲染流水线，且修边工序省不掉——省了就露出 3D 味 |
| 像素 sprite 立在 3D 场景 | 拿到真光照、景深与 tilt-shift，同时永久放弃 pixel-perfect（3D 相机下像素网格必然不对齐），并接管一整套 3D 引擎的复杂度 |
| 程序化生成纹理 | 换来零接缝零重复与近零边际成本，失去「在某块地板上藏一个故事」的能力，必须靠离散 decal 与 sprite 补回 |
| 骨骼驱动动画 | 旋转与非整数缩放进入渲染路径，像素网格纪律基本失效。要保网格就得把骨骼动画烘成帧 |
| 禁止亚像素与旋转 | 位置每帧取整、动画只能整格跳，不能用连续 tween 做 squash / stretch；手感只能靠帧安排而不是插值 |
| 整数缩放 | 窗口尺寸只能是逻辑分辨率的整数倍，其余靠 letterbox。想填满任意窗口就必须接受非整数缩放与边缘发虚 |
| 1-bit | 明暗的唯一手段变成抖动，于是抖动图案的锚定方式从美术偏好升级成核心技术问题 |
| 光照即玩法 | 光照进入每帧关键路径，必须做缓存、降级与预算监控；同时反向约束美术——不能靠环境亮度传递信息 |
| 混合像素尺寸 | 拿到清晰文本（CJK 项目常被迫如此），代价是画面出现两种像素粒度，必须靠设计明确分层，否则读作「贴上去的」 |

## 技术栈清单（十二项，逐项必须有答案）

坐标定完后逐项填。**没有答案的项就是还没做的决策，不是「以后再说」。**

1. **引擎与渲染器** — 引擎、2D 还是 3D 管线、是否需要自定义 shader 通道
2. **逻辑分辨率与缩放** — 逻辑画布尺寸、整数还是非整数缩放、letterbox 策略、放大滤镜（nearest / xBR / hqx / 自写）
3. **相机** — 是否取整、是否允许平滑滚动、zoom 是否整数、抖动与位移如何不破网格
4. **调色板技术** — 索引色渲染还是 RGB；palette swap 是否走 shader 1D LUT；是否需要 color cycling；量化在构建期还是运行期
5. **资产管线** — 绘制工具 → 导出 → 打包的完整链路（Aseprite CLI / TexturePacker / 引擎原生）。**图集必须有 padding 与 extrude**，否则过滤和缩放会吸到邻块像素（bleeding），这是像素项目的必踩坑
6. **关卡数据** — 编辑器（Tiled / LDtk / 引擎原生 / 自研）与导入路径；程序化生成占多少比例
7. **动画** — 逐帧 / 骨骼 / 程序化 / 3D 烘帧；动画帧率是否与游戏帧率解耦
8. **光照** — 无 / 烤进美术 / additive 光圈 / 法线贴图加动态点光 / 自实现遮蔽与视野。装饰还是玩法
9. **字体与文本** — bitmap font 还是像素 TTF；文本按世界 px 还是输出 px 渲染。**CJK 是硬约束**：需要 10 / 12 / 16px 点阵中文字库（Ark Pixel、Zpix 一类），字形量与内存远超拉丁字母，且大多数「像素字体」根本没有中文字形
10. **后处理** — 在像素分辨率还是输出分辨率上做；全屏 shader 的 fill-rate 预算
11. **UI 层** — 引擎内绘制还是 DOM / 原生 overlay；UI 像素尺寸是否与世界一致
12. **平台与性能预算** — 目标平台的 fill-rate 与 CPU 上限；最低端设备上哪些效果先降级

## 常见误判

- **把硬件代际当轴一。** 「16-bit 风」推不出任何技术约束；自设 16 色板与 NES 无关。
- **拿参考游戏的坐标当自己的。** 学一个参考前先在六轴上对齐。不同轴上的东西学不过来——无描边 painterly 项目去学有描边卡通派的可读性做法一定失败，因为形体分离机制根本不同。
- **把「像素完美」当默认美德。** 它只是轴五的一个位置，代价是窗口尺寸受限与手感受限。
- **只报「用了什么风格」，不报被锁死了什么。** 美术方向只写画面描述、不写它对技术栈的蕴含，等于把决策成本推给实现方。
- **忽略字体。** 中文像素项目里，字体常是第一个被发现无解的约束。
- **把 lo-fi horror 默认当像素。** 这一路里最有名的几作是低多边形 3D 加后处理，不是像素；像素分支要小得多。抄错载体会得到完全不同的技术栈。
