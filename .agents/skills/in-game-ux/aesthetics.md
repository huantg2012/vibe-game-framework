# 怎样审美过关

「好看」不是通用扁平好看，也不是本 skill 里的默认皮。**好看 = 对得起本项目 `art-direction.md` 给 UI 写的那句设备/物件定义**，由人终审。过反模式清单 ≠ 好看。agent **不许**自称审美过关。

开工闸门在 [SKILL.md](SKILL.md)。项目色板、字号、组件类、已确认丑法住在 UI Kit / palette / art-direction，本文件只给**可否决的操作定义**。

## 「好看」的操作定义（可否决句）

先从 art-direction 抄出一句话：「这个世界里的界面是什么物件打出来的字？」（终端、纸质地图、魔法镜、锈蚀开关盘……）。后续每条都应能否决一处具体样式。

1. **一句话必须能答「这是哪台机器 / 哪件物件打出来的字」。** 答不出、或答案是网页/后台/游戏外皮肤 → 否决。元界面允许「我知道这是软件」，但色板/字体/边框纪律仍守 art-direction，禁止另起一套现代扁平。
2. **层级用项目已锁定的手段，不许用新色相「做层次」。** 典型是亮度差，以 Kit 为准。多加一处高亮或未映射 hex → 否决。
3. **风格化压的是装饰密度，不是可读性。** 暗底可以，关键文字必须能读（项目 Kit 的对比度下限；未写则按对比度 ≥ 4.5:1）。人点名「看不清」时，「风格需要」不能当理由。
4. **分离与强调必须能回答物理原因。** 答「好看」就删。投影/外发光/无来由的 glow 在多数工业/设备世界里非法；若 art-direction 把某效果写成世界材质（旧屏磷光、纸纤维），才保留。
5. **P0 常驻独立信息点过多 → 否决**（默认 > 6，项目 IA 可改）。无标签裸条、只有圆点没有名字 = 失败。

## 动手顺序（先打开项目文件，再写样式）

1. 该表面 **ui spec**：载体、参考锚点、P0/P1/P2、不遮挡区。没有 → 停，先补 spec 或走 Bootstrap。
2. **architecture.md**：屏幕空间 vs 世界坐标怎么挂。不要发明第二套 overlay 根。
3. **UI Kit**（若有）：载体规则、可读性、色、字号、基元。活文档：实现一偏就改 Kit，禁止拿失效换算当验收。
4. **palette + art-direction**：每个色能答色彩架构或系统色。
5. **world 术语表**：可见字用表内词。
6. **`_template-ui.md` U1–U12** 当结构闸门。过 U2 只证明不像后台，**不能**在这里勾好看。

没有 Kit 时不要用别的游戏的组件词典顶上，走 SKILL.md Bootstrap。

## 写完自检怎么做（不只「要做」）

- **灰度**：截图把饱和度打到 0。安全/危险、可用/不可用是否仍靠位置、条长、计数、符号、标签读出。只剩色相差 → 不合格。
- **并排同一台设备**：把本游戏两个以上表面拼成一张图。边框策略、字体族、间距单位、字色档必须像同一套输出。有一张像后台 → 把新的收进现有基元。
- **物理原因**：列出 diff 里每一处非平直表现，半句写「世界里因为……」。写不出 → 删。
- **P0 ≤ 6**：数当前场景同时常驻且决策要用的独立信息点。无标签裸条 = 失败。
- **对比度**：按 Kit；次要信息优先降字号，不要把字降到读不出。不 hover 截一张：身份标签必须已经在图上。
- **朗读可见字符串**：能听成一个复合名词 → 拆成表名 / 数值 / 档位三个节点。

机械扫：圆角、投影、原生 tooltip、仅 hover、软件词、未声明的 overlay 根。

## 人终审（agent 不许自称）

可以自称并给 Grep/对比度证据：无未授权的 web 套路、色在锁定表、字号在 Kit、复用共享样式、P0 计数、字符串已拆开。

**不许**自称：好看、审美过关、像游戏、成体系、对得起参考锚、人会满意。

必须停下来给人看、人一票否决即不合格：

1. 好不好看 — 载体对了仍可又闷又丑（字挤、对齐漂、符号像 debug）。
2. 读不读作「这世界里的一台设备」。
3. 与具名参考并排是否违和 — 学了方法还是只抄了暗色。
4. 关键信息是否真的一眼能读 — 公式过了人仍可能说看不见。
5. 装饰剂量 — 是这块屏/这件物件，还是特效开太多。
6. 任何新视觉语言 — 即使人先口述了改法，仍须 art 最短核对后再进 code，再给人看一帧。

交付栏只写「机械层已扫；审美待人终审」。不要写 PASS。
