# 游戏系统评审

回答三个制作问题：**最值得保留的体验是什么；什么最妨碍它成立；下一笔制作投入应解决什么。**

评审轴从品类、玩家动机和实际行为推导。既有实现、作者反馈和旧版表现是待核对资料，不是完整的及格标准。建议必须维护作品个性，同时接受实际体验的反证。

## 确定对象与结论边界

从用户请求选择模式，不强制整盘重审：

- **整游戏**：覆盖正式入口、实际循环、关键系统与它们的交接。各领域标题齐全不等于内容覆盖完整。
- **模块专项**：聚焦指定关卡、敌人、道具、武器、成长或视听；连带核对它的获取/准备条件、使用后果及对下一步选择的影响。未审部分不能获得整体通过结论。
- **设计稿或素材审查**：仅有文档、数据、静帧时，做相应设计/表达判断，列出需要实玩的假设；没有可玩版本不妨碍提供这些有限结论。
- **迭代复评**：核验旧问题、原优势和新增回归；注明不同版本及入口，保留旧结论原来的适用范围。

先用短段说明：对象/入口/版本、品类假设、目标体验、材料、实际可做的验证与范围。预算不足时优先核心循环及高影响矛盾，公开缺口；不为了填满清单无限扩测。用户只要规范或计划时，到规范或计划为止；只要评审时，不顺手实施整改。

## 先建立评审地图

评审用两套正交结构：

1. **质量轴**：目标与选择、信息与公平、空间与节奏、美术/声音/手感、学习与重玩、可靠性与制作成本。读 [dimensions.md](references/dimensions.md)，按品类选择问题，不把战斗、永久成长、多人或随机地图当必需品。
2. **内容与状态覆盖**：登记实际系统、循环节点、常见/失败/深层状态、入口、证据及缺口。模块专项挑相关链路，整游戏逐项交代；每项标“已覆盖 / 部分覆盖 / 未覆盖 / 不适用”。不能用历史验收、代码存在或自动测试把未玩到的内容改成已覆盖。

把游戏画成实际行动链：

**玩家目标 → 可获得的信息 → 选项与成本 → 输入 → 系统后果 → 玩家理解 → 下一次选择。**

观察三个时间尺度：一次行动、一次完整活动或出行、多次循环。每个发现落到链上的具体关系；纯艺术表达也有独立价值，不必先证明它改变按键选择。

## 信息披露与工作方式

默认先体验、后解释；用户明确要求知情设计审查或材料不足时，直接说明采用的模式。

- **A 首次接触**：只给正常玩家能得到的简介、教程、操作、正式入口和必要运行说明。保留原教程。记录实际看到、预期、行动、结果与理解，先封存首轮判断。
- **B 定向复核**：将观察转成可推翻的假设，比较有意义的状态或替代行动，寻找竞争解释。深层预置状态与自然成长分开。
- **C 创作意图对照**：再读取世界观、设计、美术目标、用户约束和旧反馈；分别写“意图 / 所见 / 差距”。解释不能抹去已经发生的误解；偏离品类惯例也不自动是缺陷。
- **D 实现诊断**：按需要查代码、数据、生成器、素材和性能，定位原因与制作成本。优先调查高影响问题，不用通读仓库替代实玩。

已参与制作、已看旧评审或被环境注入背景的代理是**知情专家**。无法消除的先验照实披露；不能声称严格盲测。AI 专家和多代理共识均不是真人用户研究。

可并行时，让独立职责互补：制作/设计负责完整循环与价值，美术负责归类和品质，技术美术/工程负责因果诊断和生产可行性。真正首次接触者使用新上下文，只收到任务所需的原始材料；不把怀疑的问题和预期结论喂给他们。各组先独立留证，协调者按同一玩家事件合并根因、保留分歧，不用投票代替证据。子代理只能执行其获分配的审查范围。

## 美术是独立主项

有视觉材料时读 [art-review.md](references/art-review.md)。完整评审默认给美术约三分之一的取证与判断投入；这是关注度，不是加权分数或凑篇幅，用户的专项范围优先。

必须给出**美术设计归类**，再独立判断表达力度、身份、完成度与玩法适配。不能只写“像素风”“可读”“通过绘制规范”。声音和手感分别下结论，不拿静帧或音频播放状态充作验证。

风格归类描述所见，不自动成为创作指令：不默认低饱和、写实、更多细节、统一色温或全面增亮更好。混合风格按组织关系判断；审美判断写清观察依据，不能伪装成自动检查结果。

## 取证、裁决与改进

执行前读 [evidence-and-delivery.md](references/evidence-and-delivery.md)，按任务选择自然体验、受控复现、数据分析和技术测试。证据保存到项目既有 QA 位置或本次隔离目录；不修改用户正式存档。

每个领域判为**成立 / 脆弱 / 不成立 / 未验证**，附适用范围。不把领域平均成总分。美术身份和持续观感的问题可以独立影响交付，不默认降成末尾的轻微修饰。

每个重要问题至少写清：

- 情境、信息、预期、实际结果与玩家后果；附具体证据入口。
- 属于实现错误、设计关系失效、表达误导、艺术品质问题，还是证据缺口；允许多因，但避免一因多次计数。
- 严重度、影响范围、发生频率和证据把握分别标明；保留反证及竞争解释。
- 建议、收益、代价/风险、依赖、粗略工作量、最小验证及通过条件。未知成本就写未知，不用虚假的精确工期。

优先修断裂的核心因果，再检验不成立的设计关系，最后按收益推进内容与表现。小输入、清楚效果可以产生深决策；条目数量、机制复杂度、地图种子数都不是深度证明。对系统性问题优先提出共享规则/管线层面的修复，并明确应覆盖哪些产物和状态，不能只修好展示样例。

交付可简可详，但必须包含：范围与缺口、核心判断、值得保护的优势、独立美术结论（适用时）、最重要的问题及证据、优化顺序和验收方式。完整格式与问题记录字段见证据参考。用户若要求“是否接受此前反馈”，逐条回答接受/部分接受/不接受/待验证及理由；评审建议不等于获得作者最终批准。

## 本项目接入与长期使用

在《那天之后》/ `coh` 仓库使用时，协调者在C/D阶段读 [coh-context.md](references/coh-context.md)；其他项目跳过。必要的仓库执行规则仍先遵守，但其中透露的先验要记入披露范围。

本 skill 管方法，项目活 spec 管机制，当前用户意图管创作方向。项目数字、旧问题、旧评分和阶段状态不复制为固定门槛。长任务保存覆盖台账、已封存观察、待复核问题和下一步，恢复会话时从缺口继续。复评用新证据更新问题状态，不覆盖原始观察，不把实现完成、内部通过与用户验收混为一谈。
