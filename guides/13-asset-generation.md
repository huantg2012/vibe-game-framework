# 多模态资产生成工作流

## 概述

游戏的美术和音频资产由外部 AI 工具生成（Midjourney、Stable Diffusion、Suno 等）。Claude Code 本身不直接生成图片/音频，而是：

1. **生成 prompt**（基于风格指南 + 世界观约束）
2. **引导人使用外部工具**（推荐工具 + 参数建议）
3. **评估结果**（一致性检查 + 迭代反馈）
4. **管理资产**（命名、归档、追溯）

---

## 资产类型与推荐工具

### 视觉资产

| 资产类型 | 推荐工具 | 说明 |
| -------- | -------- | ---- |
| 角色/敌人 | Midjourney / SD + LoRA | 风格一致性靠固定 prompt 前缀 |
| 场景/背景 | Midjourney / SD | 大尺寸，注意无缝拼接需求 |
| UI 元素 | SD (ControlNet) / 代码 SVG | 规则形状优先代码生成 |
| 图标 | Midjourney / SD | 统一视角、统一底色 |
| 特效/粒子 | 代码生成（Canvas/WebGL） | AI 生成静态帧不如代码动态效果 |
| 像素风 | SD + pixel art LoRA | 如果选了像素风格 |

### 音频资产

| 资产类型 | 推荐工具 | 说明 |
| -------- | -------- | ---- |
| BGM（背景音乐） | Suno / Udio | 按场景/情绪生成，通常 2-5 首够用 |
| 音效（UI） | ElevenLabs SFX / Freesound | 点击、悬停、确认、取消等 |
| 音效（游戏内） | ElevenLabs SFX / Freesound | 攻击、受击、拾取、升级等 |
| 环境音 | Freesound / AI 混合 | 风声、水声、火焰等循环音 |
| 语音（如有） | ElevenLabs / F5-TTS | 通常 indie 游戏不需要 |

## 视觉统一性原则：Degree not Kind

**所有视觉变化是同一套语言的参数调节，不是切换语言。**

这条原则适用于所有资产生成和评审环节。目标是让玩家在游戏的所有场景、实体、UI 中感到"这些属于同一个游戏"——不是靠让一切长得一样，而是靠共享底层视觉语法。

### 实操检验

- **新资产评审时**：和已有资产并排放一起看——它们读起来像同一个游戏的截图吗？如果不像，问题不是新资产本身，是它偏离了已建立的视觉语言
- **表达递进（如污染浓度轻→重）时**：只调参数（大小、密度、亮度、色相），不换表达方式。递进是连续渐变，不是阶梯跳变
- **区域差异**：靠底层参数（色温、材质纹理）区分，不靠改变上层表达方式（污染的画法）
- **新内容类型**：引入新视觉元素前，先确认它和已有的视觉语法不矛盾

### 违反信号

- 两个资产放一起看像不同游戏
- 同一种现象（如"污染"）在不同场景用了完全不同的视觉表达
- 浓度/等级递进中间有"画风突变"断层
- 新区域的视觉和其他区域没有任何共享元素

## 工作流：从需求到游戏内可用资产

```
┌────────────────────────────────────────────────────┐
│ 1. 需求确认                                         │
│    Art Agent 从 Task Brief 了解需要什么资产          │
│    读取 art-direction.md + world.md 确认约束        │
├────────────────────────────────────────────────────┤
│ 2. Prompt 生成                                      │
│    Art Agent 输出完整 prompt（含工具、参数、后处理）  │
├────────────────────────────────────────────────────┤
│ 3. 人执行生成                                       │
│    在外部工具中使用 prompt → 得到候选图/音频         │
├────────────────────────────────────────────────────┤
│ 4. 评估与筛选                                       │
│    人初筛 + Art Agent 做一致性检查（可选）           │
├────────────────────────────────────────────────────┤
│ 5. 迭代（如果不满意）                               │
│    人描述问题 → Art Agent 调整 prompt → 重新生成    │
├────────────────────────────────────────────────────┤
│ 6. 后处理                                           │
│    已提交管线按 config 执行：去背/调色/降采样/量化/裁切补齐 │
│    npm run art:postprocess -- --config <配置路径>   │
│    npm run art:verify -- --config <配置路径>        │
├────────────────────────────────────────────────────┤
│ 7. 集成到项目                                       │
│    放入指定目录 + 注册到资产清单                     │
└────────────────────────────────────────────────────┘
```

## Prompt 生成规范

### Art Agent 输出 prompt 时必须包含

```markdown
## Asset: [资产名]
用途：[在游戏中的位置]
工具：[Midjourney / SD / Suno / ...]
尺寸：[WxH px]（视觉）或 时长：[秒]（音频）
格式：[PNG/WebP/SVG/MP3/OGG]

### 生成 Prompt
[完整 prompt，包含风格前缀]

### 反向 Prompt（SD 用）
[排除项]

### 工具参数建议
[模型版本、采样器、CFG、步数等建议值]

### 后处理步骤
1. [具体操作]
2. [具体操作]

### 一致性检查点
- [ ] 色彩是否符合 art-direction 的色彩方案
- [ ] 风格是否与已有资产统一
- [ ] 是否符合 world.md 的约束（材质/元素/禁忌）
```

### 风格一致性的关键：固定前缀

为保持所有资产风格统一，在 `art-direction.md` 中定义一个**固定 prompt 前缀**：

```markdown
## Prompt 固定前缀（所有视觉资产共用）

### Midjourney
[style prefix, e.g. "flat vector illustration, limited color palette, 
thick outlines, slightly whimsical, game asset on transparent background"]

### Stable Diffusion
[model: xxx, positive prefix: "...", negative prefix: "..."]
```

所有资产的 prompt 都以这个前缀开头，确保视觉语言一致。

```markdown

## BGM 规划
| 场景 | 情绪 | 风格描述 | 参考 |
| ---- | ---- | -------- | ---- |

| 战斗 | [情绪] | [描述] | [参考曲目] |
| 探索 | [情绪] | [描述] | [参考曲目] |

## 音效风格
- 整体质感：[像素感 / 写实 / 卡通 / 合成器]
- UI 音效：[短促清脆 / 柔和 / 机械感]

- 格式：[MP3 / OGG / WAV]
```

## 资产管理

### 目录结构

```
assets/
├── images/
│   ├── characters/      ← 角色/敌人立绘
│   ├── backgrounds/     ← 场景背景
│   ├── ui/              ← UI 元素
│   ├── icons/           ← 图标
│   └── effects/         ← 特效帧/序列
├── audio/
│   ├── bgm/             ← 背景音乐
│   ├── sfx/             ← 音效
│   └── ambient/         ← 环境音
└── _sources/            ← 原始生成文件（未后处理的，备查）
    ├── [asset-name]_raw.png
    └── [asset-name]_prompt.md  ← 生成该资产用的 prompt 记录
```

### 命名规范

```
[类型]-[名称]-[变体].格式

示例：
  char-skeleton-warrior-idle.png
  bg-dungeon-entrance.png
  icon-item-iron-sword.png
  bgm-battle-01.mp3
  sfx-hit-sword.ogg
```

### 资产追溯

`assets/_sources/` 目录保存每个资产的生成记录：
- 使用的完整 prompt
- 使用的工具和参数
- 生成日期
- 后处理步骤

作用：如果需要生成"同风格的新资产"，可以找到原始 prompt 作为基础。

## 一致性保障

### 问题：AI 生成的多个资产之间风格不统一怎么办？

### 解决方案

1. **固定 prompt 前缀**（首要手段）— 所有同类资产使用相同的风格描述前缀
2. **参考图约束**（SD img2img / MJ --sref）— 用第一张满意的图作为后续生成的风格参考
3. **批量生成+筛选**（而非逐个生成）— 一次生成 4-8 张，筛选风格最统一的
4. **后处理统一**（管线执行）— 去背、降采样、色板量化是必须执行的确定性阶段，不是可选补丁；色调统一用于保持跨批次资产一致。以上处理均由已提交的后处理管线按 config 执行。

### 一致性检查流程

当一批资产生成完成后：
1. 放在一起并排查看 — 有没有明显"不属于同一个游戏"的
2. 对照 art-direction.md 的色彩方案 — 主色/辅色/强调色是否一致
3. 对照 world.md 的约束 — 有没有出现不该出现的元素
4. 如果不一致 → 淘汰离群项，用风格最统一的作为下一轮的参考

## 谁来跑后处理

- **Art Agent**：产出后处理 config、用于外部生图的完整 prompt，以及“什么算通过”的验收标准；不运行脚本。
- **人**：在外部生图模型中使用 prompt 生成原图；在机器验收通过后，对最终资产做肉眼审美判断。
- **Code Agent**：运行后处理和机器验收命令，并以 `art:verify` 的退出码判断是否通过：

  ```bash
  npm run art:postprocess -- --config <配置路径>
  npm run art:verify -- --config <配置路径>
  ```

  `art:verify` 退出码为 0 表示机器验收通过；非 0 表示不通过。
- **任何人**：都可手动运行上述 `npm run` 命令作为兜底。

验收失败时按原因分流：

```text
art:verify 非 0
├─ 原图本身不合格（主体、构图、风格或内容不满足要求）
│  └─ 回到“人执行生成”：人使用调整后的 prompt 重新生成原图
└─ config 参数不合适（阶段顺序、尺寸、阈值、色板等）
   └─ Art Agent / Code Agent 调整 config → Code Agent 重跑 postprocess + verify
```

## 在 Slice 中的触发时机

| 情况 | 何时生成资产 |
| ---- | ------------ |
| Foundation 阶段 | 生成风格参考图（不是最终资产，是探索方向） |
| 系统 Slice | 为验证功能生成最少量的占位资产 |
| 内容 Slice | 为新内容批量生成对应资产 |
| 打磨 Slice | 替换占位资产为最终品质 / 统一调整风格 |
| 专门的资产 Slice | 集中时间批量生产一类资产 |

**原则：早期用占位（甚至纯色方块），只在确认设计稳定后投入正式资产生成。** 避免"精心生成的资产因为设计改了而作废"。

**正式资产要求：** 每个正式视觉资产在集成前都必须经过 `npm run art:postprocess -- --config <配置路径>` 和 `npm run art:verify -- --config <配置路径>`；仅有机器验收通过还不替代人的审美判断。
