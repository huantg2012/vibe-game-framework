# 阶段2: Design（设计）

## 目标

将 Concept Doc 展开为可直接指导开发的设计规格。这一阶段结束后，任何一个 Code Agent 拿到设计文档就能开始写代码，不需要猜测。

**输入**：Concept Doc（来自 Ideation）
**输出**：GDD精简版 + 技术架构方案 + 美术方向文档

---

## 本阶段的核心矛盾

设计阶段的诱惑是"把一切想清楚再动手"。但对 Solo+AI 项目，正确姿势是：

> 只设计到"能开始做原型"的程度，剩下的在做的过程中迭代。

设计文档是**活文档**，不是蓝图。它的目的是对齐方向，不是穷尽细节。

---

## 子步骤

```
Step 1: 系统拆解      →  游戏由哪些系统组成？
Step 2: 核心系统设计  →  最关键的1-2个系统的详细规则
Step 3: 技术架构      →  用什么技术、怎么组织代码
Step 4: 美术方向      →  视觉风格、资产规格
Step 5: GDD 整合      →  输出完整设计文档
```

---

## Step 1: 系统拆解

### 你做什么

- 回顾 Concept Doc 中的核心循环和机制
- 判断 AI 拆出的系统列表是否合理
- 标注优先级：哪些系统是原型阶段必须的

### AI Agent 做什么

**角色：系统架构师**

- 将核心循环拆解为独立系统（如：移动系统、战斗系统、经济系统、UI系统等）
- 画出系统间的依赖关系
- 建议原型阶段只需实现哪些系统

### 产出

```markdown
## 系统列表

| 系统 | 职责 | 原型阶段 | 依赖 |
| ---- | ---- | -------- | ---- |
| [系统A] | [做什么] | 必须 | 无 |
| [系统B] | [做什么] | 必须 | 系统A |
| [系统C] | [做什么] | 可选 | 系统A, B |

## 系统依赖图
[文字描述或 mermaid 图]

## 原型范围
仅实现：[系统列表]
```

### Prompt 策略

```
这是我的游戏概念文档：[粘贴 Concept Doc]

请帮我将这个游戏拆解为独立的系统模块：
1. 列出所有需要的系统，每个系统一句话描述职责
2. 画出系统间的依赖关系（谁依赖谁）
3. 标注哪些是原型阶段必须实现的（目标：最少系统验证核心体验）
```

---

## Step 2: 核心系统设计

### 你做什么

- 选择 1-2 个最核心的系统进入详细设计
- 对 AI 给出的规则做"这感觉对/不对"的判断
- 提出边界情况让 AI 补充

### AI Agent 做什么

**角色：游戏设计师**

对选定的核心系统，输出完整的设计规格：

- 规则定义（状态、输入、转换规则）
- 数值框架（不是最终数值，而是数值结构）
- 玩家感知（玩家看到什么、操作什么、得到什么反馈）
- 边界情况（极端情况怎么处理）

### 产出：系统设计 Spec 模板

```markdown
# 系统设计：[系统名]

## 概述
[一段话描述这个系统做什么、为什么存在]

## 状态模型
[这个系统管理哪些数据/状态]

## 规则
1. [规则1]：当[条件]时，[结果]
2. [规则2]：...

## 玩家交互
- 输入：[玩家能做什么操作]
- 反馈：[系统怎么告诉玩家发生了什么]

## 数值结构
| 参数 | 含义 | 初始范围 | 调节目的 |
| ---- | ---- | -------- | -------- |
| [参数A] | [含义] | [x-y] | [影响什么体验] |

## 边界情况
- 如果[极端情况A]：[处理方式]
- 如果[极端情况B]：[处理方式]

## 与其他系统的接口
- 输入来源：[从哪个系统获取数据]
- 输出目标：[将结果传给哪个系统]
```

### Prompt 策略

```
我要详细设计 [系统名]。
它在核心循环中的作用是：[作用]
它支撑的体验支柱是：[支柱]

请给出完整的系统设计规格，包含：
1. 状态模型（管理哪些数据）
2. 规则（用"当X时Y"的格式，穷尽核心规则）
3. 玩家交互（操作和反馈）
4. 数值结构（不要给具体数值，给参数框架）
5. 边界情况（至少3个极端case）
6. 与其他系统的接口

设计粒度：够写代码但不过度限制实现方式。
```

## Step 3: 技术架构

### 你做什么

- 基于你的技术偏好和经验做最终选型
- 审核项目结构是否合理
- 确认你能维护这个架构

### AI Agent 做什么

**角色：Tech Lead**

- 基于游戏类型和系统复杂度推荐具体技术方案
- 设计项目目录结构
- 定义模块边界和通信方式
- 给出关键技术决策的 pros/cons

### 产出

```markdown
# 技术架构

## 技术选型

| 层 | 选择 | 理由 | 备选 |
| -- | ---- | ---- | ---- |
| 游戏引擎/框架 | [xxx] | [理由] | [备选] |
| 语言 | TypeScript | [理由] | - |
| 构建工具 | Vite | [理由] | - |
| UI框架 | [xxx] | [理由] | [备选] |
| 状态管理 | [xxx] | [理由] | [备选] |
| 部署 | [xxx] | [理由] | - |

## 项目结构

[目录树]

## 模块通信方式
[事件驱动 / 直接调用 / ECS / 等]

## 关键架构决策
1. [决策]：选[A]不选[B]，因为[原因]
2. ...
```

### Prompt 策略

```
游戏概况：[类型、核心机制、复杂度]
系统列表：[从Step1粘贴]
约束条件：
- Web浏览器运行
- TypeScript
- Solo+AI开发，需要AI能高效生成代码
- 要能快速迭代（热更新）

请设计技术架构：
1. 推荐具体的框架/库，给理由和备选
2. 设计项目目录结构
3. 定义模块间怎么通信
4. 标注最关键的2-3个架构决策，给 pros/cons

倾向：简单优先，不要过度工程化。能用简单方案解决的不要引入复杂抽象。
```

## Step 4: 美术方向

### 你做什么

- 提供你喜欢的视觉参考（截图、游戏名、关键词）
- 选择 AI 给出的风格方向
- 确认资产规格可行（你能用 AI 生成出来）

### AI Agent 做什么

**角色：Art Director**

- 基于游戏调性推荐视觉风格方向
- 确定可被 AI 生成的美术风格（避免选需要高度手绘一致性的风格）
- 定义资产规格（尺寸、格式、命名）
- 给出风格关键词和参考 prompt

### 产出

```markdown
# 美术方向

## 视觉风格
[风格描述 + 关键词]

## 为什么选这个风格
- 符合游戏调性：[解释]
- AI可生成性高：[解释]
- 一致性容易维护：[解释]

## 色彩方案
- 主色：[用途]
- 辅色：[用途]
- 强调色：[用途]

## 资产规格
| 类型 | 尺寸 | 格式 | 生成方式 |
| ---- | ---- | ---- | -------- |
| 角色 | [px] | PNG | AI生成+后处理 |
| 背景 | [px] | PNG/SVG | AI生成 |
| UI元素 | [px] | SVG | 代码/AI | 
| 图标 | [px] | SVG | AI生成 |

## AI 生成 Prompt 模板
- 角色：[base prompt template]
- 场景：[base prompt template]
- UI：[base prompt template]

## 风格参考
[3-5个参考图/游戏截图的描述]
```

### Prompt 策略

```
游戏类型：[类型]
核心体验调性：[紧张/轻松/神秘/欢快/...]
技术约束：Web游戏，需要加载快
生成约束：美术靠AI生成，需要选一个AI擅长且容易保持一致性的风格

请推荐 3 种视觉风格方向：
每种包含：风格描述、为什么适合、AI生成难度评估、参考关键词
重点考虑：AI是否容易生成一致的资产（比如像素风比写实风更容易保持一致）

我喜欢的参考：[你的参考]
```

## Step 5: GDD 整合

### 你做什么

- 审核整合后的 GDD，确保无矛盾
- 标注"待原型验证"的设计假设
- 正式确认进入原型阶段

### AI Agent 做什么

**角色：文档整合者**

将 Step 1-4 产出合并为一份完整的 GDD，同时生成 CLAUDE.md 的初版（供后续 Agent 使用）。

### 产出

两份文件：
1. `docs/gdd-core.md` — 完整 GDD
2. `CLAUDE.md` — 项目 AI 入口文件（初版）

## 本阶段的 Agent 配置

Design 阶段开始出现**多角色但可串行**的情况：

| 步骤 | 建议会话方式 | 原因 |
| ---- | ------------ | ---- |
| Step 1-2 | 一个会话 | 系统拆解和设计有强连续性 |
| Step 3 | 可以新会话 | 技术选型是独立决策，需要的上下文不同 |
| Step 4 | 可以新会话 | 美术方向是独立领域 |
| Step 5 | 新会话 | 整合工作，需要加载前几步全部产出 |

上下文传递方式：每步产出写入文件 → 下一步从文件加载。

---

## 质量门禁：Design → Prototype

- [ ] 核心系统有完整的规则定义（能直接翻译为代码）
- [ ] 技术方案已验证可行（跑通了 hello world 级别的技术验证）
- [ ] 美术风格已确定且 AI 能稳定生成
- [ ] CLAUDE.md 已就位，新会话能快速上手
- [ ] 设计文档中标注了"待验证"的假设（原型阶段要测的）

---

## 常见陷阱

| 陷阱 | 症状 | 解药 |
| ---- | ---- | ---- |
| 过度设计 | Spec 写了20页还没开始写代码 | 只详细设计原型要做的1-2个系统 |
| 技术镀金 | 选了炫酷但复杂的方案 | 问自己"最无聊的方案能不能用？" |
| 美术焦虑 | 纠结风格定不下来 | 选"AI最容易保持一致"的那个 |
| 忽略接口 | 系统内部想清楚了但系统间怎么连没想 | Step 2 强制要求写接口定义 |
